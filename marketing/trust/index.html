The sync tool that would rather stop than guess.

icloud-md keeps a folder of Markdown files and your Apple Notes in two-way sync. Before any write, it proves it can rebuild the note byte-for-byte. When it can’t be certain a change is safe, it refuses and tells you why — it never overwrites silently.

$ icloud-md status Comparing against iCloud… M Trip planning.md will push edit ! Reading list.md refused: changed remotely since the last pull — run "pull" first $ icloud-md pull merged: Reading list.md (2 remote edits, 1 local edit) conflict: Trip planning.md — both sides edited line 12 wrote standard conflict markers; resolve, then push
A refusal, not a failure. The note changed on another device since your last sync. Rather than pick a side, push declines and points at the safe next step.
Real three-way merge. Non-overlapping edits from both sides merge automatically. Only a genuine collision — same lines, both sides — asks a human.
Conflicts look like git. Standard <<<<<<< markers, in the file, in your editor. No proprietary resolution UI.

Above: the failure modes, on purpose. A sync tool is defined by what it does when it isn’t sure.

Convenience is the wrong thing to optimize

Most sync tools treat a silent overwrite as an acceptable cost of feeling seamless. For notes, that trade is backwards: a failed sync costs you a retry, but a wrong overwrite costs you the sentence you can’t get back — and you may not notice for weeks.

icloud-md is built on the opposite premise. Every ambiguous situation is an error with a name and a next step, never a guess. Slightly more friction, in exchange for never wondering what happened to a note.

The safety model, concretely

  • rule 1Prove the round trip before writing. Push fetches the note’s current server version and verifies it can rebuild it byte-for-byte from its own understanding. Only then is your edit applied and re-verified. A note the tool can’t fully parse stays read-only.
  • rule 2Writes are optimistically locked. Every push carries the change tag from your last sync. If the note moved on since then, the server rejects the write and it's reported as a conflict — the remote copy is never clobbered.
  • rule 3Merge only what can’t collide. Pull runs a real diff3 across base, local, and remote. Overlapping edits become explicit conflict markers for you to resolve; the tool never picks a winner.
  • rule 4Refuse the rest, loudly. Attachment-bearing notes, table reorders, formatting the tool can’t faithfully reproduce — all named refusals in status output, not silent skips and not risky writes.

Your undo button for the last six months

Every pull or push that changes a note snapshots it first, and whole-note epochs tie a note and its tables together in time. history lists the timeline, diff compares any two points, and revert writes a known-good version back to the server — the escape hatch if a bad edit ever does land, whoever's fault it was.

icloud-md history "Trip planning.md"
icloud-md diff "Trip planning.md" a1b2c3..d4e5f6
icloud-md revert "Trip planning.md" a1b2c3   # asks before writing

Built to fail loudly — the details

What happens on a genuine conflict?
Pull writes standard diff3 conflict markers into the file. Until you resolve them, that note won’t push and won’t be re-merged — the tool won’t compound a conflict.
What if Apple changes the service?
Then things fail — visibly. This tool speaks the private API iCloud.com itself uses, and every response is parsed strictly: unexpected shapes become errors and refusals, not corrupted writes.
What does “refused” actually look like?
A named reason on the status/push line for that note: changed remotely since the last pull, has a file attachment, still contains conflict markers. Every refusal states its remedy.
Is my account safe to point this at?
Treat it as powerful and unofficial: keep the clone in a git repo, try a disposable note before notes you care about, and read the honest print below.

Said plainly: this is not an Apple product. It reverse-engineers the private CloudKit web service that iCloud.com’s own Notes page uses, cross-checked against Apple’s own client code — but Apple can change any of it without notice, and accounts with Advanced Data Protection aren’t supported.

The entire design exists because that risk is real: byte-for-byte verification, optimistic locks, named refusals, and local version history are what “safe enough to use anyway” looks like. Keep backups regardless. Free and open source, MIT.
